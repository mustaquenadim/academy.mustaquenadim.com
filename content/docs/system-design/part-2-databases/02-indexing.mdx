## The problem

Your users table has 50 million rows and the login page is timing out. You look at the query — `WHERE email = ?` — and it seems trivial. But the database is reading every single row to find the one that matches, because email is not indexed.

That is a *full table scan*: 50 million comparisons for one login. At a few hundred logins per second, the disk and CPU are pinned and everything else queues behind it. The data is fine. The problem is that the database has no faster way to *find* things than looking at all of them.

## A first attempt

The naive fix is "add more hardware." A bigger machine reads rows faster, so the scan finishes sooner. But you have only pushed the wall further out — a scan is still `O(n)`, so doubling the data doubles the work no matter how fast the box.

The real cost is the algorithm. Searching an unordered list is linear. If instead the data were *sorted* by email, you could binary-search it in `O(log n)` — about 26 comparisons for 50 million rows instead of 50 million. But you cannot keep the table itself sorted by every column you query. You need a separate, sorted structure that points back into the table.

## The insight

Build a **secondary sorted structure keyed by the column you search**, and let it point at the rows. That is an index.

The workhorse is the **B-tree** (really a B+ tree): a wide, shallow, balanced tree that stays sorted as you insert and delete. Because each node holds hundreds of keys, the tree is only 3–4 levels deep even for billions of rows, so a lookup is a handful of disk reads instead of a full scan. Range queries (`created_at BETWEEN …`) work too, because siblings are linked in sorted order.

A **hash index** is the other shape: it maps a key straight to a location in `O(1)`, unbeatable for exact-match lookups — but it cannot do ranges or sorting, because a hash throws ordering away.

## How it works

<Steps>

<Step>

### The index stores keys in sorted order

Instead of scanning the table, the database walks a B-tree keyed on `email`. Each step discards most of the remaining keys, so it reaches the leaf in `O(log n)`.

</Step>

<Step>

### The leaf points back to the row

The leaf holds a pointer (a row id or the primary key) to the actual row on disk. One more read fetches the full record. This second hop is why indexes are not free reads.

</Step>

<Step>

### A covering index skips the second hop

If the index already contains every column the query needs, the database answers straight from the index and never touches the table. That turns two reads into one.

</Step>

<Step>

### Composite indexes follow the leftmost-prefix rule

An index on `(country, city)` helps queries filtering by `country`, or `country AND city`, but not by `city` alone — because the keys are sorted by country first. Order the columns to match your most common filters.

</Step>

<Step>

### Every write must update every index

Inserting a row means inserting into the table *and* into each index that covers it, keeping every B-tree balanced. More indexes means slower writes and more storage.

</Step>

</Steps>

```
   Query: WHERE email = 'ana@x.com'

        B-tree index on email                Table (heap)
        ─────────────────────                ────────────
              [ m ]                           row 8123301
             /     \                          ┌────────────────────┐
          [ f ]    [ t ]                       │ id | name | email…  │
          /   \    /   \        pointer         │ ...                │
       …ana…  …    …   …   ─────────────────►   │ ana@x.com  ✓        │
       O(log n) to the leaf                     └────────────────────┘
                                                one extra read
```

## Concrete numbers

On 50 million rows, a full scan reads all 50M rows; a B-tree lookup touches roughly `log₂(50,000,000) ≈ 26` keys, in practice 3–4 disk pages because each node is wide. That is the difference between a query that takes seconds and one that takes under a millisecond.

The write cost is real. Each additional index typically adds 10–20% to insert time and its own storage — an index can be 20–40% of the size of the column it covers. A table with eight indexes can spend more time maintaining indexes than writing the row itself. That is why write-heavy tables carry few indexes and read-heavy tables carry many.

## When to use it

<Callout type="warn" title="The trade-off">
An index makes reads fast and writes slower. You are spending write throughput and disk to buy read latency. Index the columns you filter, join, and sort on — and resist indexing everything, because unused indexes cost you on every insert while helping no query.
</Callout>

<Callout type="idea" title="Watch for low selectivity">
An index on a column with few distinct values (a boolean `is_active`, a status with three states) barely helps — half the table still matches, so the planner may scan anyway. Indexes pay off when a lookup eliminates most of the rows.
</Callout>

## Practice

<Accordions>

<Accordion title="You have an index on (last_name, first_name). Which of these queries can use it: filter by last_name, by first_name, by both?">

`last_name` alone and `last_name AND first_name` both use the index, because the keys are sorted by last name first. Filtering by `first_name` alone *cannot* use it — first names are scattered across the whole index with no ordering the database can jump into. This is the leftmost-prefix rule: a composite index only helps queries that start from its left.

</Accordion>

<Accordion title="Your query is 'SELECT count(*) FROM orders WHERE status = shipped'. When would a covering index help most?">

If the index is on `(status)` and includes nothing else, the database still finds matching entries in the index without touching the table — for a count it never needs the row bodies, so it is already covering. The win is largest when the query reads only indexed columns; adding an unindexed column to the SELECT forces the second hop back to the table for every match.

</Accordion>

<Accordion title="Why can a hash index beat a B-tree for exact lookups but be useless for a dashboard showing 'orders from the last 7 days'?">

A hash index maps a key to a location in `O(1)`, faster than a B-tree's `O(log n)` for exact matches. But a hash destroys ordering — there is no notion of "next key" — so a range like `created_at >= now() - 7d` cannot be walked. Range and sort queries need the B-tree's sorted leaves.

</Accordion>

</Accordions>

## Recap

- A full scan is `O(n)`; an index turns lookups into `O(log n)` (B-tree) or `O(1)` (hash).
- B-trees also serve ranges and sorts; hash indexes only serve exact matches.
- Every index speeds reads but slows writes and costs storage — index deliberately.
