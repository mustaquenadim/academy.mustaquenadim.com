## The problem

Your servers live in Virginia. Your users live everywhere. A user in Sydney requests your homepage image, and every byte crawls ~16,000 km across the Pacific and back. The image is fine; the *distance* is the problem.

It gets worse under load. Launch a popular video and thousands of far-away users all pull the same large file from that one Virginia datacenter, saturating its outbound bandwidth and stacking a fat speed-of-light delay on top. Everyone far away has a bad time, and your origin servers strain to push the same bytes over and over. You cannot move Sydney closer — so you must move the *content*.

## A first attempt

The obvious fix: buy a bigger server and a fatter pipe in Virginia.

But this is a **latency** problem, not a bandwidth one, and no upgrade in Virginia shortens the road to Sydney. A Sydney↔Virginia round trip is ~200 ms set by the speed of light — untouchable from Virginia. Meanwhile the same bytes are shipped across the ocean thousands of times because nothing near the user remembers them. Scaling *up* one location cannot fix a problem caused by *distance*. You need presence in many locations at once.

## The insight

Keep **copies of your content in many locations worldwide**, and serve each user from the one nearest them.

That network of geographically distributed cache servers is a **CDN**. Put a copy of your image on **edge servers** in Sydney, Frankfurt, São Paulo, Tokyo — hundreds of cities. Now the Sydney user's request travels a few dozen kilometers, not sixteen thousand. The edge caches your content on first request and serves everyone else locally. You attack latency by collapsing distance, and you shield your origin because the edge answers most requests without ever touching it.

## How it works

<Steps>

<Step>

### DNS sends users to the nearest edge

When a user resolves your CDN hostname, the CDN's DNS returns the IP of the closest, healthiest edge location (by geography/network path). The user connects to an edge a few milliseconds away instead of your distant origin.

</Step>

<Step>

### Cache hit — served locally

If that edge already has the file cached, it returns it immediately. No trip to the origin. This is the fast path and, for static content, the overwhelming majority of requests.

</Step>

<Step>

### Cache miss — fetch once from origin

On the first request (or after expiry), the edge fetches the file from your origin, stores it locally with a TTL, and serves it. The *next* user in that region gets a hit. One origin fetch serves a whole region.

</Step>

<Step>

### Expiry and invalidation

Cached objects carry a TTL (via `Cache-Control`). When it expires the edge re-validates with the origin. When you change a file *before* expiry, you issue a **purge/invalidation** or change the URL (`app.v2.js`, or a content hash) to force fresh fetches.

</Step>

</Steps>

Same request, without and with a CDN:

```
WITHOUT CDN                         WITH CDN
                                    Sydney user ─► [ Sydney edge ]  ~5 ms
Sydney user ──────────► Virginia                       │ (cache miss, once)
   ~200 ms round trip    origin                        ▼
   every request, every user                     [ Virginia origin ]
                                    next Sydney users ─► edge  (cache hit, no origin)
```

## The numbers

- **Latency win:** a far-away static asset drops from ~150–250 ms (cross-ocean origin) to ~5–30 ms (local edge) — often a **5–10×** improvement.
- **Cache hit ratio:** a well-tuned CDN serves **85–99%** of static requests from the edge, so your origin sees only the misses.
- **Origin offload:** at a 95% hit ratio, your origin handles **1 in 20** requests — a 20× traffic reduction and matching bandwidth savings.
- **Scale:** major CDNs run **hundreds of PoPs** across the globe, so almost every user is within ~50 ms of an edge.
- **TTL tuning:** static assets get long TTLs (hours–days); frequently changing pages get short TTLs (seconds–minutes) or are cached only after careful invalidation planning.

<Callout type="warn" title="Static is easy, dynamic is the hard part">
CDNs shine on **static** content — images, video, CSS/JS, fonts — that is identical for everyone and safe to cache long. **Dynamic**, per-user content (your account page, a personalized feed) is risky to cache: serve it to the wrong user and you leak their data. Options are short TTLs, caching only the static shell, or edge compute — but "just cache everything" is how you ship one user's data to another.
</Callout>

<Callout type="idea" title="Cache invalidation is the catch">
Copies scattered across hundreds of edges are wonderful until you need to change one. Nothing updates instantly — you either wait out the TTL, issue a global purge (seconds to minutes to propagate), or sidestep it entirely with versioned/hashed URLs so new content simply has a new address. Plan how you will invalidate *before* you cache.
</Callout>

## Practice

<Accordions>

<Accordion title="Why can't you fix cross-continent slowness by upgrading your origin server?">

Because it is a latency problem set by distance, and the origin's location does not change. A Sydney↔Virginia round trip is ~200 ms no matter how powerful the Virginia box is — the speed of light is the limit. A CDN fixes it by serving from an edge in Sydney (~5 ms away), collapsing the distance itself. Bigger origin hardware only helps a bandwidth or compute bottleneck, not the round-trip delay.

</Accordion>

<Accordion title="At a 95% cache hit ratio, how much traffic does your origin actually see?">

Only the 5% of requests that miss — roughly 1 in 20, a ~20× reduction in load and bandwidth on the origin. That offload is often as valuable as the latency win: it lets a modest origin survive traffic spikes and viral moments, because the edge absorbs the flood of repeated reads for the same static objects. Push the hit ratio up with longer TTLs and versioned URLs and the origin barely notices peak traffic.

</Accordion>

<Accordion title="You pushed a critical CSS fix but users still see the broken old file. Why, and how do you prevent it?">

The old CSS is still cached at edges under its unchanged URL and TTL, so users keep getting the stale copy until it expires. Fix it now with a purge/invalidation of that file. Prevent it in future with **versioned URLs** — `styles.a1b2c3.css` (content hash) or `styles.v2.css` — so any change produces a *new* URL that was never cached, sidestepping invalidation entirely. This is why build tools fingerprint asset filenames.

</Accordion>

</Accordions>

## Recap

- A CDN keeps **copies of content at edge servers worldwide** and serves each user from the nearest one, attacking latency by collapsing distance.
- **Cache hits** serve locally in milliseconds; **misses** fetch once from origin — yielding both a big latency win and heavy **origin offload**.
- CDNs excel at **static** content; **dynamic/personalized** content and **cache invalidation** are the genuine hard parts — plan versioning and TTLs deliberately.

<Callout type="idea" title="In an interview">
Whenever a system has a global audience or serves heavy static assets, propose a CDN early and justify it as a *latency* fix (distance) plus *origin offload*. Score extra points by volunteering the hard part unprompted: how you will handle cache invalidation (versioned URLs) and what you will *not* cache (per-user dynamic content).
</Callout>
